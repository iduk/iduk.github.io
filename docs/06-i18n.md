# 06. 한글·영문 병행 설계

결정: **한글을 기본으로 하고 영문을 병행한다.** 이 문서는 01~05번 문서에 걸치는 다국어 규칙을 한곳에 모은 것이다. 충돌하면 이 문서가 우선한다.

## 1. 주소 체계

| 언어 | 주소 | 비고 |
|---|---|---|
| 한글(기본) | `/`, `/work/`, `/work/<slug>/` | 기존 검색 노출과 옛 주소 이동이 한글 기준이라 접두어를 붙이지 않는다 |
| 영문 | `/en/`, `/en/work/`, `/en/work/<slug>/` | |

- 슬러그는 두 언어가 같다(`jejuair-mobile` 등). 언어 전환은 같은 슬러그의 다른 언어 주소로 간다.
- 옛 주소 `/portfolio/<slug>/`는 한글 상세로 이동(301). 영문 옛 주소는 없다.
- **브라우저 언어에 따른 자동 이동은 하지 않는다.** 정적 호스팅에서는 서버 쪽 언어 판별이 안 되고, 검색 로봇과 공유 링크가 엉킨다. 대신 헤더에 언어 전환 링크를 둔다.
- 대안으로 `/ko/`, `/en/`을 모두 접두어로 두는 방식이 있으나, 루트에서 언어를 골라 이동시키는 처리가 필요해서 채택하지 않았다.

## 2. Astro 설정

```js
// astro.config.mjs (발췌)
i18n: {
  defaultLocale: 'ko',
  locales: ['ko', 'en'],
  routing: { prefixDefaultLocale: false },
},
integrations: [sitemap({ i18n: { defaultLocale: 'ko', locales: { ko: 'ko-KR', en: 'en-US' } } })],
```

- 페이지 본체는 `src/views/`에 한 벌만 두고, `src/pages/`(한글)와 `src/pages/en/`(영문)에는 언어만 넘기는 얇은 파일을 둔다. 두 언어 화면이 어긋나지 않게 하기 위함이다.
- 현재 언어는 `Astro.currentLocale`로 읽는다.

## 3. 콘텐츠 구조

사람이 읽는 문자열 필드는 두 언어를 함께 가진다.

```ts
const L = z.object({ ko: z.string().min(1), en: z.string().min(1) });
// projects/<slug>.json
{ slug, year, title: L, role: L, summary: L, tags: ['ui', 'dashboard'],
  cover: { image, alt: L }, blocks: [{ type: 'image', image, alt: L }, ...] }
```

- `en`이 비면 **빌드가 실패**한다. 영문이 없는 글이 한글 사이트에 섞여 나오지 않는다.
- 프로젝트 제목은 대부분 원래 영문이라 `title.en`은 원제 그대로, `title.ko`는 같거나 한글 표기로 한다.
- **태그는 키로 저장하고 표시 이름은 `tags.json`에서 언어별로 가져온다.** 기존 태그에 한글(예: "반응형웹")과 영문(예: "Dashboard UI")이 섞여 있으므로 정리 때 키를 정한다.
- 기간·연도 표기는 빌드 때 `Intl.DateTimeFormat`으로 언어별 형식을 만든다.
- 화면 문구(메뉴, 버튼, 푸터, 404)는 `src/i18n/ui.ts`에 `ko`, `en` 사전으로 둔다. 키 집합이 같은지 단위 테스트로 검사한다.

## 4. 번역 작업 방식

| 대상 | 규모(추정) | 방법 |
|---|---|---|
| 역할·한 줄 설명 | 글 24개 × 2필드 | 기존 한글 본문에서 뽑은 문장을 영문으로 번역 |
| 이미지 `alt` | 약 60개 | 두 언어 모두 새로 작성 |
| 태그 이름 | 정리 후 20~30개 | 표로 정리 |
| 화면 문구 | 20여 개 | 사전 |

- 초안은 Claude가 작성하고, **사용자가 영문을 검토한다(S05의 🛑 항목에 추가).** 직무 용어(UI/UX, 대시보드 등)는 업계 통용어로 맞춘다.
- 기존 글에 한글만 있는 부분은 영문 초안을 만들고, 영문만 있는 제목은 한글 초안을 만든다.
- 번역 초안은 사용자가 확정하기 전에 `status: draft-translation` 표시로 두고, 확정되면 지운다. 이 표시가 남아 있으면 CI가 실패한다.

## 5. 화면과 타이포

- `<html lang>`은 페이지 언어를 따른다. 언어가 섞이는 구간(영문 제목 안의 한글 등)은 `lang` 속성을 붙인다.
- 줄바꿈: `:lang(ko) { word-break: keep-all }`. 영문은 `text-wrap: balance`와 `hyphens: manual`.
- 같은 크기 토큰이어도 영문은 글자가 넓고 한글은 좁아서 히어로 자간을 언어별로 따로 둔다(`:lang(en)`에서 `-0.04em`, `:lang(ko)`에서 `-0.045em` 정도로 시작해 눈으로 조정).
- Pretendard는 라틴 문자도 포함하므로 글꼴은 추가하지 않는다. 영문 페이지는 한글 서브셋을 받지 않아서 글꼴 전송량이 줄어든다.
- 헤더에 언어 전환 `KO | EN`. 현재 언어는 `aria-current`, 링크에 `hreflang`과 `lang`을 붙인다. 전환 링크는 같은 페이지의 상대 언어 주소로 가며 JS가 필요 없다.
- 긴 영문 제목은 한글보다 줄이 늘어나므로 목록 행과 이전·다음 링크가 두 줄로 넘어가도 깨지지 않게 한다.

## 6. SEO

- 모든 페이지에 `<link rel="alternate" hreflang="ko|en|x-default">`를 상호 연결한다. `x-default`는 한글.
- 정규 주소(`canonical`)는 각 언어 자기 자신.
- 사이트맵은 `@astrojs/sitemap`의 i18n 옵션으로 언어쌍을 연결한다.
- 열린 그래프: `og:locale`(`ko_KR`, `en_US`)와 `og:locale:alternate`. 제목·설명은 언어별.
- 구조화 데이터(JSON-LD)는 쓰지 않는다(07번 문서와 05번 S11). 언어는 `<html lang>`, `hreflang`, `og:locale`이 나타낸다.
- 열린 그래프 이미지(`/og/<slug>.jpg`)는 두 언어가 공유하고, `og:image:alt`는 해당 언어의 대표 이미지 alt를 쓴다.
- 검색 콘솔에서 두 언어 주소가 모두 색인되는지 공개 2주 뒤 확인한다.

## 7. 보안과 호스팅

- CSP, 헤더, 방화벽 규칙은 언어와 무관하게 동일하다. `/en/*`도 같은 정책을 받는다.
- 404는 정적 파일 하나(`404.html`)만 서비스되므로 **한 페이지 안에 두 언어 안내를 함께 쓴다.**
- `/html/*` 데모는 번역하지 않는다(번역 없음, 연락처만 07번 문서에 따라 교체). 영문 상세 페이지의 데모 링크 옆에 "한글 페이지입니다" 대신 `lang="ko"` 표시만 한다.
- 리다이렉트는 02번 문서와 같고 `/en/` 아래 별도 규칙은 없다.

## 8. 테스트 기준

- 한글 페이지마다 영문 쌍이 있고, 서로의 `hreflang`이 상호 연결되어 있다(자동 검사).
- 두 언어 모두 axe 위반 0, 두 언어 모두 Lighthouse 모바일 95 이상.
- 360px에서 영문·한글 모두 가로 스크롤이 없고 제목이 잘리지 않는다.
- 언어 전환 링크가 같은 슬러그의 반대 언어 주소로 간다(전체 24개 글).
- `ui.ts`의 두 사전 키가 같다. 콘텐츠의 모든 `L` 필드에 `ko`, `en`이 있다.
